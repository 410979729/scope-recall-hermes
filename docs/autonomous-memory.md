# 无人值守记忆

## 日常如何工作

1. Hermes 捕获用户输入和工具观察，原文、来源身份、时间、词法索引在同一事务中保存。明确的偏好、决定、更正和未知实质内容进入加工队列；纯“收到”、空成功回执等只保留来源，不制造长期待办。它们仍可被词法检索，也仍参与会话来源关联。
2. 主机捕获成功、压缩前和会话结束会唤醒合并后的 worker。worker 有次数、时间、队列和辅助模型预算上限。缺少模型或向量能力时，对应队列等待能力恢复，不消耗失败次数。
3. 自动召回将当前问题证据与最多两条有效偏好/约束、一个有可靠来源的当前任务共同装入有界上下文。所有背景内容仍保留主语、来源与适用条件；无关背景不会让“没有答案”变成“有证据支持”。模型显式调用 `recall` 工具（Hermes 工具与 Codex MCP）而查询本身没有找到证据时，不附带偏好/约束背景，结果为 `no_match`；只有查询明说要继续某个任务（如“继续”“接着做”，不含“继续用 X 吗”这种问要不要接着用的说法）且存在唯一有来源的当前任务时，仍附带该任务。显式历史查询不会混入当前任务。
4. “继续任务”在普通召回缺少任务时最多补查一次。多个任务无法确定唯一目标时保留歧义，不靠最近时间擅自选一个。关系检索限制两跳、最多 24 个对象。
5. 明确的“换成”“调整为”“停止使用”等可以直接更正或撤回唯一目标，原版本与原文保留。目标查找先按相关内容过滤再限量，记忆增多也不会漏掉目标。引用、否定、疑问、条件、已识别的未来表达不会走立即修改通道；自然语言不明确时仅保存原文，不猜测授权。
6. 问题点名了某一天（“9月29日”“September 29”“on the 29th”、带年份的完整日期、“昨天”“昨晚”，一到三天），而且除去日期和入口名之后，整句就是在问或请求那天说了什么、做了什么（“聊了什么”“帮我看看都做了哪些工作”“总结一下”“有什么进展”“what did we talk about”），召回会直接读那一天的对话：提问者能看到的范围内，发给 agent 的消息和 agent 给出的回复，按时间均匀取几条；二十个字以内、只是应答的消息（“继续”“好的，继续吧”“按你说的做”）不取；点名几天时各天平分名额、轮流排在前面，没有消息的那天把名额让给其他天。同时点名了共享库的入口（“工作机 Claude Code 9月29日聊了什么”）时只读该入口的对话。别的提到日期的消息不读那一天的全部对话，按下一条召回：问的是具体的事（“9月2日发布的那个版本修了什么”“继续昨天的任务”），那天没提过的事不会拿那天的消息来答；只是顺口提到日期（“今天在吗”“我今天在忙呢”“今晚做什么菜”“请继续昨天做的”），也不会因为读了整天的对话把偏好和当前任务挤掉；句子里多出这类问法以外的内容，就不读整天的对话。日期范围（“9月28日到30日”）、上周这类时段、超过三天、未来的日子和 9999-12-31 这类占位日期，都不读整天的对话。一天按主机告诉模型的时区划分，与召回结果里显示的时间一致：Hermes 用它配置里的 `timezone`（没有配置时用本机时区），Codex 和 Claude Code 用本机时区并按当天的夏令时计算；远程入口用提供服务的那台机器的时区。
7. 问题里写明的时间按规则读成若干整天，时区与上一条相同：某一天（“9月18日”“2026-09-18”“September 18”“Sept 18th”“on the 18th”“昨天”）、一段日子（“9月6日到9月8日之间”“从7月25日到7月27日”“between Sep 6 and Sep 8”“from Jul 28 to Jul 30”“Sep 6-8”）、一个月（“9月”“in August”）、上周、这周、上个月、这个月，以及某个时间之前或之后（“9月18日之前”“since last week”）。读的只是消息可能说过的过去的日子，且只认这些明确的写法：“May I”“on the 2nd floor”“马上周末”“这周边”“本周期”都不算时间，“最近”“recently”也不算一段时间；一天中的某段（“今晚”“今早”“tonight”“this morning”，上一条按日读对话时仍算那一天）、明天和下周这类还没到的日子、写进标识里的日期（“release-2026-09-18”“id2026-09-18”）、9999-12-31 这类占位日期、超过三个时间的列举都不读；写反的范围（“9月8日到9月6日”）读作同样的几天。按历史或某一时刻读取（`history`、`as_of`）时不读时间，召回与以前一样。读出时间后，召回在这段时间里按问题的其余部分再找一遍，与之共有足够多词的消息（其余部分只有一个词时要有这个词，否则至少两个、且不少于三成）一并召回，时间本身的写法（“18th”）不要求消息里出现；这段时间里说的内容排在其他时间同一话题的内容前面，其他时间的内容照常召回，不会因为日期不对被去掉。没写时间的问题读不出时间，召回与以前完全一样。
8. 召回结果的 `answerability` 只说证据能否回答问题，不改变取回的内容。没有取回与问题相关的内容，或问题点名了一两样东西（不在英文句首、以大写字母开头的词，或中文问题里的拉丁词；I、全大写的缩写、月份和星期不算）而没有一条取回的内容回答它，是 `unknown`。答案可能不全（读取失败或没读完，相关内容因过期或预算被去掉，比较缺一边、问原因缺原因、要继续却没有有来源的任务），或问题没有点名任何东西而取回的内容没法按问题核对（全小写的英文问题、不含拉丁词的中文问题、问某一天的问题、超过 120 个字符或带代码块的提示、点名超过两样东西的提示），是 `partial`。问“哪个”“which”这类要人选择的问题，回答它的内容来自不止一个来源（一条主张和它出自的那条消息算一个来源），是 `ambiguous`。问题点名了它问的东西，并有内容既提到它、又说到问题里的另一个词（问题除了名字什么都没问时，提到名字即可），是 `supported`。只用来引出请求的词不算问题问的词（召回时仍照常按它们查找）：tell me、describe、explain、any updates、the latest、介绍一下、说说、讲讲、关于……知道、怎么样、……的情况、进展等，所以“介绍一下 Orchard”和“Orchard 是什么”一样，提到 Orchard 的内容即可回答，“介绍一下 Orchard 的端口”仍要说到端口；status（status page）、情况下（条件），以及说明请求关于谁的 me 和我（contact me、给我订）仍算问的词。能回答问题的只有：主人自己说的话，引号里转述的话（按句式和引出它的说话者、来源或冒号识别，大写标题式或不分词的中文也算）和提问、假设、猜测、转述的句子除外，引号只括住一个词、名称、标识或数值时仍算主人自己的话；嵌套引号按内外配对，Orchard's 中的撇号不关闭引用；users' choices 这类所有格需有后续配对的闭引号及所有格语境，其间的嵌套引号照常配对；'Blue Cypress'、‘Blue Cypress’ 和 'The Alps' 这类名称末尾的引号正常闭合，The 加一个大写名称不算所有格；名称里的「称」不引出引语；有效的主张，主人自己的否定回答（“我不吃辣”）也算；只因单一来源不够有力、还在等首次评估的主张；以及问题明说要继续某个任务时（祈使或疑问，句前可有短应答，如“好的，继续做迁移”“请你继续做”“继续吧”“继续上次”“恢复上次”“继续做迁移”“继续搞迁移”“继续 H100”“继续当前任务”“接着做”“恢复上次的任务”“OK, continue the …”“So where were we”“let's continue Orchard”“can we pick up Orchard”“where were we”；否定请求、普通陈述如“We will continue the migration”“我们继续做”、鼓励或别的动词如“继续努力”“继续观察”，以及问要不要接着用的“继续用 X 吗”不算），该任务有来源支撑的进度。助手的猜测、工具输出、已被评估为证据不足的提议、仍是提议的否定、问的不是继续时的任务进度、产物的名称和指代，都不算回答。

记忆只从对话写入：主机经由钩子交来的每一轮（Hermes 的 provider 钩子，客户端的 hook）都存为来源，worker 按同一套接收与主张规则从中提炼。别的插件记下的候选不会被接收，也不会为它们出具晋升回执：不支持 memory stack 契约（候选由别的插件记录、回执由召回出具）。MCP 客户端的 `propose_memory` 只把一条提议存为助手可见的来源，并返回这次捕获的回执；它是提炼的依据之一，本身不是已接受的事实。

`source_only` 是正常处理结果；`deferred` 表示容量不足、以后有限补入。两者存储在内部调度元数据中，不会被当成缺失证据，不会发送给提炼模型。

工具输出有两种情况在捕获时直接按 `source_only` 处理：与本 scope 内更早一条工具输出内容完全相同的重复（`tool_output_repeat`），以及更早版本的捕获过滤器为被省略的输出留下的占位摘要（`tool_output_omitted`）。两者都不嵌入、不进入整理；重复的工具输出原文与词法索引照常保留。占位摘要只按其中工具自己的报错文字建词法索引（有的话），其余不建：其余的词全是信封自带的（tool、status、exit_code……），导入的大量占位摘要会把这些常用词推过高频词上限，提问里的这些词就被丢掉了。更早版本建的多余索引用 `unindex-withheld-outputs` 清掉（见 `install.md`）。

其余工具输出也不进入整理：原文和词法索引照常保留，一直能按字查到；向量保留 `tool_output_retention_days` 天（默认 180 天），这段时间里也能按意思查到。但不从中提炼记忆事实（`DERIVATION_ROOT_ORIGINS` 里没有工具输出，接收时只排向量任务）。agent 读过、运行过的内容不是它该记住的东西；怎么做一类任务，由主机提炼成技能。从工具输出提炼出的多是文件大小、路径、端口、创建时间这类事实，数量会远超真正值得记住的内容，主人的提问却用不到它们。更早版本提炼出、还没确认的这类事实，用 `retire-rootless-claims` 撤下（见 `install.md`）。

## 默认边界

| 项目 | 默认值与行为 |
| --- | --- |
| 加工队列容量 | 每 scope/project/branch 的 pending+leased 普通总上限 2048，重要内容总预留 128，均分给 consolidate、embed 两个独立队列；允许先排一类，另一类延期，缺失的可选向量能力不会阻塞记忆提炼 |
| 延后补入 | 每次 drain 前至多检查 16 个 deferred 来源，仍检查容量、来源当前版本与权限；两小时内持久化的用户输入与工具观察先补入，并可使用重要内容预留，但不会因此被记为重要内容 |
| 低价值来源 | 不生成昂贵工作；可信调用方可用 `MemoryCore.records.schedule_source` 按需加工，不重置已有失败任务 |
| worker 单次 | 最多 32 项，最长 120 秒；模型请求最长 45 秒 |
| 新鲜对话优先 | 每次 drain 的第 2、4、6… 次领取优先选择两小时内持久化的用户输入（提炼、向量）、工具观察与助手可见回复（仅向量），其中按可用时间先后；删除清理始终最先，其余领取保持 FIFO，积压每次 drain 至少占一半领取。该通道只检查最近可用的 512 项，超出部分仍按 FIFO 处理 |
| 唤醒间隔 | 默认 30 秒；在固定 project/branch 内按完全相同的授权 scope 集合合并，最多 8 组，每组一个执行进程和一个尾随进程；超过容量明确报告缺口，不合并权限。共享 writer 仍串行，等待前驱、锁等待与执行共用同一期限 |
| 当日加工上限 | 默认不限（`daily_work_limit` 为 0）；设了上限时，达到后只执行删除清理 |
| 临时失败 | 三次尝试后，冷却一小时，最多自动恢复两次；累计 attempt 不清零 |
| 永久错误 | 权限、推导不合法等不自动复活；来源被删除、撤权或替代的工作作废 |
| 模型费用 | 独立辅助模型账本限制调用数、输入输出、费用；自动恢复不扩张、不重置预算；预算拒绝暂停加工 |
| 自动背景 | 最多两条偏好/约束与一个任务；候选扫描上限 24，偏好文本每条最多 768 UTF-8 字节；共享最终 packet 上限 |
| 召回预算 | `budget_tokens` 按 `core/recall_budget.py` 与分词器无关的估算单位计；装不下最小有效信封时明确拒绝，不返回超限数据 |

`runtime-config.json` 的可信配置可覆盖 `daily_work_limit`（0–1000000，**0 表示不限**，默认即 0）、`auto_retry_cooldown_seconds`（60–86400）、`max_auto_recoveries`（0–4）、`worker_min_interval_seconds`（1–3600），以及 `max_items`、`request_seconds`、`drain_seconds`。修改后下一次进程加载生效。上限是保护措施，不意味着推荐把它们调到最大。

`daily_work_limit` 不是花费闸门：金额、调用数与 token 由辅助模型账本（`runtime/model_budget.py`）在每次请求前于 `BEGIN IMMEDIATE` 事务中按五道独立上限强制执行。该计数只限制每天尝试多少个队列项，且看不到任何一项的成本。一条来源会产生多个工作项（提炼、向量等），把它设成低于每天实际产生的工作项数，结果不是省钱而是永久积压：每天处理不完的部分只增不减。

辅助模型必须显式配置并有预算账本。模型不可用时，原文与词法召回仍正常，提炼的偏好/任务不会凭空生成。Core 嵌入方可通过 `CoreConfig.admission_policy` 设置 `AdmissionPolicy`；运行时默认使用上表值。主机配置不是用户聊天或模型工具参数，不能用聊天文本修改身份、范围或预算。

OpenCode Go 的提炼路由允许显式设置 `consolidation.reasoning_effort: "none"`，以及 `response_format: {"type": "json_object"}`；其他 OpenAI 兼容路由的 `reasoning_effort` 只接受 `low`、`high`、`max`。各服务关闭推理的参数不同，以所用服务的文档为准。

## 生命周期与故障

有效时间、已撤回/被替代版本、删除/抑制、来源版本和权限都由 SQLite 事实层判定，背景召回复用相同的读取与最终释放检查。过期内容不进入当前背景；没有有效截止时间的事实不会仅因变旧而自动删除。自动“遗忘”体现为当前视图排除失效内容，不会擅自擦除审计来源。显式删除按授权流程立即阻断读取并优先清理派生数据。

同一 Hermes 进程里，压缩前与结束时只重试已经观察过且捕获失败的原始 DTO；不会把无来源 ID 的摘要冒充用户原文，也不宣称能恢复进程崩溃前从未捕获的消息。长时停机、缺少凭据和耗尽预算需要环境恢复，插件不会无限调用模型来“自愈”。后台恢复由后续主机活动或 `autostart` 的定时唤醒触发。

`doctor` 显示 pending/leased/failed、最老待办、最近工作器结果和最近成功时间，并汇总当前可见且未抑制的 `source_only_sources`、`deferred_sources` 和最早延后来源时间。计数单位为当前来源分段；长消息可对应多个分段。待办年龄使用最初持久化时间，不因重试时间后移而清零。`--python` 会报告目标解释器实际加载的包版本、位置和版本不匹配，不能把“可以 import”当成新版本已经装好。`runtime-worker-status.json` 只存有限状态元数据，异常回执不包含模型文本或凭据。状态显示成功不等同于每条事实语义正确。条件适用采用字面匹配，复杂条件、多人物关系和任意自然语言更正仍有保守拒绝边界。

## 安装与回退

按 `install.md` 在独立环境安装。部署前先备份对应实例的数据及配置。正常卸载默认保留 Core 数据；不要把 purge 当作回退操作。重新安装旧版本时也使用备份的环境与数据库。
