# P07：情景、恢复状态与产物版本

本文件说明隔离候选的写入和读取边界。P07 提交供 G1 独立审计；它不表示 P08/P09 自动检索、P11/P12 宿主接入或发布验收已经通过。

`core/composition.py` 在 P03 的同一 SQLite 事务边界中提供 `episodes`、`episode_sources`、`accept_consolidation`、`register_artifact`、`artifact`、`open_artifact`、`reference` 和 `purge_attachments`。新库 schema 为 1105。旧生产库迁移和整套维护命令在 P14/P15 验收，不由导入模块触发。

## 情景和恢复状态

可靠 task anchor 与 scope/project/branch 共同确定情景身份；跨会话仍可接续。没有 task anchor 时，只有实际观察到的同一产物版本能够连接唯一已有情景，否则采用同会话的 provisional 区间。明确换题开始新情景，相同标题不合并不同项目或无锚点的新会话。

每段最多保存 200 个事件的归属与摘要依赖，超过后建立同 series 的下一段。读取原始来源支持有限分页，摘要记录 `processed_sequence`、来源版本和 watermark，新增或修订来源会标明未处理尾部或需要重建；旧摘要不能作为最新自动交付结果。这里尚未实现 P08 的带 epoch 的不透明集合游标。

状态区分 open/completed/failed/cancelled/interrupted/unknown。助手承诺不构成完成；普通闲聊不制造目标；暂停不等于取消；时间按规范化 UTC 排序，迟到的旧失败不覆盖已有的较新完成记录。规则是保守的确定性资格检查，不能单凭这些正则宣称已经理解所有自然语言。

恢复摘要必须逐字引用有效来源。目标与决定需要原始人类来源；验证进展需要完整的人类确认或实际工具观察，拒绝假设、否定、问题和助手承诺的错误晋升。受控导入的人类身份只在已批准 TEST 导入清单的精确指纹匹配后生效。模型不会获得可信 context 的构造权限。

验证进展依赖来源当时的 environment revision。新工作区中添加一个事件，或重新提交旧进展的摘要，均不能把旧环境验证变成新验证。读取会标记 `needs_revalidation`。

## 产物和指代

产物使用稳定 ID 与整数版本，名称和路径不承担身份。注册需要已捕获的产物来源和运行时授权的绝对路径、媒体类型、大小上限、预期 SHA-256。只保留获准文件，内容以哈希寻址写入实例自身的 retained 目录。同路径被覆盖后，旧版本仍能按原字节打开。

读取再次核对 installation/agent、作用域、来源、删除状态、大小和哈希，返回 `(Artifact, bytes)`。只存描述或原文件缺失时返回明确缺口；不会根据描述生成图片冒充原件。PNG/WebP 的本地边界测试验证魔数与读写规则；实际开发切片使用通过 XML 解析的 SVG，不把魔数夹具当作真实图片渲染验收。

Windows 长路径只在文件 I/O 层转成扩展路径，权限判断保留规范化逻辑路径；符号链接和 junction 祖先被拒绝。删除只处理归属本次 tombstone 的附件，仍有合法引用的共享 blob 保留。事务失败可能留下未引用的 CAS 文件，完整物理清理清单由 P15 覆盖；在线可见性仍立即关闭。

指代候选只能指向可访问、真实出现的产物版本。展示序号必须来自实际 observed snapshot；第 0 张无效。工具和助手不能代替用户消歧。同名身份冲突不能靠模型少报候选变成唯一；版本号必须与所指名称相连。后续明确澄清创建新的 binding revision，保留历史并使旧派生恢复状态失效。

M11 的项目改名复用 Claim：已有、同范围且当前有效的命名事实提供稳定目标，独立 alias Claim 保存有来源的新称和目标引用，原命名事实及旧称保留。人类原文必须明确把目标的名称或稳定 subject 改为完整新称；普通提及新名、同范围无关事实、其他项目、问句和假设均不能建立关系。这里验证写入结构和原文依据，自动别名检索仍属于 P08；产物名称关系使用已有版本化 ReferenceBinding，不另建项目真值表。

## 模型输入与实际开发证据

`core/consolidate.py:consolidation_messages` 是可复用的纯输入格式器：最多 32 条已授权原始来源、最多 16000 UTF-8 字节，附真实 schema、角色、来源版本、水位和已观察到的产物版本。它不接收答案、后续查询或预置 Claim。传输与调度位于核心之外；接受提议时，在同一个写事务中重新校验全部来源、权限和依赖，任一错误回滚整个提议。

`probes/p07_development_slice.py` 在 TEST 中写入六条自然会话/工具记录和两个同名 SVG 版本，向 MiMo V2.5 请求结构提议，然后在独立核心会话重新释放对象和打开原件。最后向无此前聊天历史的 DeepSeek V4 Flash 提交当前请求与实际读回的证据。归档位于 `verification/P07/development-v1`、`development-v2` 和 `development-artifact-manifest.json`。

这条早期链实际发生了原文 → 模型提议 → 核心验源入库 → 新会话重新读回 → 原件字节校验 → 独立回答。它使用显式可信任务选择；统一自动检索和 RecallPacket 编译仍由 P08/P09 实现。这不是两个正式宿主的 L4 或 J01 全旅程通过证明。

所有失败保留：提取 10–12 分别被候选/版本格式、来源引用格式和助手计划资格检查拒绝；13 接受。回答 14 网络错误并保留满额预留；15 错将未消歧理解为尚未被用户认可；16 正确读回版号、配色、布局和下一步，但仍询问后续配色方向，未完成实际编辑。提取 13 的 `open_items` 为空，未完成事实仍保存在带来源的 decision 原文中；不能据此声称恢复字段分类完全正确。

开发输入公开可见，密封留出集不用于调参。费用由共享 TEST 台账计入失败和重试：归档时 16 次尝试的已计费或保守预留总额为 72,396 micro-USD，即 $0.072396，包含此前探针；这是 API 折算核算，不是服务商账单。已批准上限仍为 $20。

另一个 J02 简化切片使用实际运行的清单导出脚本，先验证排序，再在缺失输出目录处真实失败，随后记录暂停指令。在新进程和不同文件指纹的现场恢复时，旧验证被标为需要复核，脚本确实重新运行：排序通过，导出仍失败。真实提取 20 与新上下文回答 21 使用已批准的 Go DeepSeek V4 Flash；回答根据当前错误给出了创建目录的修正代码和验证计划，未谎称已经执行，但末尾仍有询问，未记为正式宿主 L4 通过。

J02 的 MiMo 尝试 17–18 引文与序列化原文不符，19 把含“尚未修复”的整句放入验证进展并改写阻塞描述，均被拒绝。工具捕获随后采用实际 stdout/stderr 原文与实际退出码，完整 argv/脚本/时间仍在原始运行记录中。失败版本与成功版本分别保留在 `verification/P07/failure-resume-v1` 至 `failure-resume-v4`；早期两版有源记录/时序/现场标识缺陷，不计入成功分母。最新台账 `model-budget-snapshot-21.json` 为 21 次尝试，含失败及未知用量预留共 $0.080957。

## 验证与后续归属

确定性测试覆盖暂停/失败/中断/会话和分支隔离、精确原文和角色、旧环境、201 事件分段、产物版本、真实展示序、后续澄清、否定和假设、删除后缓存释放，以及文件完整性。P05 intention 的写入/取消/删除契约继续复用；提醒触发与去重由 P08–P10 验收。

独立预审发现截取“没有确认”为“确认”、截取“不要执行”为已授权下一步的漏洞。核心现检查引文所在子句的否定和限制是否完整保留，同时拒绝疑问充当目标、决定或已授权下一步。完整的负面决定仍可保存，独立肯定子句仍可执行；新的实际 Core 回归同时验证拒绝、事务回滚和这些正例。

同一来源资格检查也覆盖无问号的中文问句、捕获时的更正快路径、删除授权和否定的取消语句。恢复状态的产物引用必须有精确版本的展示证据或该版本的注册来源；仅仅见过稳定产物 ID 或旧版，不能替另一个版本提供证据。

P07 全部命令与失败保留在该任务收据及 manifest。旧测试包装器曾在 pytest 成功后清理失败，却提前写入成功收据：`episodes-1788683179161848700.json` 保持原样，但总体结果必须按失败计。现包装器在清理结束后才写最终收据，分别记录 pytest、wrapper、cleanup 与 overall 状态，并增加故障回归测试。Windows 无符号链接创建权限时的那一项明确 skip；junction 和 hardlink 实际验证单列。

G1 裁决前 P07 保持未完成，P08 不开始产品实现。后续仍需完成自动相关性与证据完整性、持久 worker、实际 Hermes/Codex 接入、完整迁移清理、留出四组对照和两个宿主的完整旅程。
