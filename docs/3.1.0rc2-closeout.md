# Scope Recall 3.1.0rc2

This candidate combines the three R1 execution branches from baseline
`68e7f410cd95bdbab00a7e8810b662de6fddf5ee`. Protocol remains 1.1; SQLite schema
advances from 1107 to 1108. It is a local integration candidate, not evidence
of a public release or an upgrade of any running assistant.

## Resulting behavior

- Claims bind first-person statements to verified host identity and preserve
  evidence, conditions, negation and correction history.
- Candidate processing shares the existing durable worker and fact-write
  transaction. The runtime forwards its candidate evaluator with the same
  per-request deadline as ordinary consolidation.
- A source matching more than 16 candidates keeps a durable remainder.
  Background processing resumes one bounded page per pass without requiring
  another user message; deleted or superseded evidence cannot continue it.
  Matching reserves its limit for the source's exact scope, project and branch,
  so visible candidates from another partition cannot starve eligible ones.
- Explicit provider rejections (429, rate limiting, and selected temporary
  5xx failures) use the existing three-attempt durable limit and backoff.
  Unknown outcomes, interrupted attempts and invalid semantic results retain
  the no-blind-retry fence. These are distinct from waiting for more evidence.
- Host authorization is supplied by the Hermes or Codex adapter. Current-person
  profile and entity views use verified principal identity.
- Four new runtime modules are included in the wheel allowlist.

## Integration repairs

The integration fixed the missing runtime candidate interface, bounded evidence
continuation, and Chinese old-value-to-new-value assertion support. The latter
still rejects old values, negated or hypothetical changes, questions and
cross-sentence evidence splicing.

Two stale test fixtures were repaired: a simulated 1106 database now excludes
1108-only tables, and capture interruption targets the actual
`record_host_event` entry. Production migration was not weakened to accept a
database falsely labelled as an older schema.

Original failed checks and later repair evidence remain in the integration
delivery receipt. Verification is targeted and offline unless the receipt
explicitly says otherwise. No full suite, private production-data processing,
embedding rebuild or real-model semantic benchmark is implied.

## Operational boundary

No running TianShu, TianJi or other Hermes installation is upgraded by producing
this candidate. Previously recorded production state must be refreshed before
any live migration. The model provider's availability and budget still bound
processing throughput; this release does not promise zero backlog under
unlimited input or automatic recovery of an uncertain external request result.
